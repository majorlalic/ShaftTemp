# 测温系统交接

## 第1章 系统边界与总体架构

本系统面向“竖井-楼层分区测温告警”场景，核心能力：

- 接收测温实时数据
- 维护 Redis 实时状态
- 保存原始数据/告警原文
- 生成告警主单与事件
- 告警合并、处警、恢复
- （设备离线）

系统为双模块，逻辑独立、数据库共享：

- `iotservice`：接入层（MQTT/HTTP），负责收包、格式归一、转发。
- `onlineservice`：业务层，负责映射、规则、告警、查询、巡检。

高层数据流：

1. 设备上送 MQTT 数据到 `iotservice`
2. `iotservice` 解析后调用 `onlineservice` 接口
3. `onlineservice` 通过分区绑定解析到 `device/monitor/floor`
4. 更新 Redis、写 raw_data/alarm_raw
5. 命中规则时写 alarm + event
6. 查询接口返回告警与实时统计

## 第2章 双模块设计与职责

### 2.1 iotservice（接入层）

定位：协议接入与消息归一，不做最终告警合并决策。

主要职责：

- 订阅 MQTT 主题（Measure/Alarm）
- 兼容数组 payload 与单条 payload
- 提取并透传关键字段：`topic/iotCode/PartitionId/dataReference/timestamp`
- 调用 `onlineservice` 批量接口

关键接口（对内）：

- `POST /shaft/iot/data/batch`
- `POST /shaft/iot/alarm/batch`

建议关注类（以当前工程命名为准）：

- `IotIngestController`：接收/转发入口
- 批量请求 VO：`Measure`、`Alarm` 请求模型

### 2.2 onlineservice（业务层）

定位：业务核心。

主要职责：

- 分区绑定解析（device/monitor/floor）
- Redis 缓存实时状态
- 规则评估与告警生成
- 告警状态流转、事件写入
- 巡检任务（离线告警）
- 全部查询接口输出

核心类与核心方法：

- `DeviceResolverService`
  - `resolve(...)`：按 `iotCode+partitionId / dataReference / partitionCode` 解析绑定
  - `refreshBindingCache()`：刷新绑定缓存（已做容错，脏绑定跳过并记录日志）
- `ReportIngestService`
  - 处理测温/告警上报主流程，串联“解析-缓存-落库-规则”
- `RealtimeStateService`
  - 维护最近上报、窗口值、活跃告警、事件限频标记
- `AlarmRuleResolverService`
  - 从 `ALARM_RULE` 加载有效规则
- `AlarmRuleEngine`
  - 输出规则命中结果（定温、差温、升温速率、离线、断纤）
- `AlarmMergeService`
  - `createOrMerge(...)`：告警主入口（新建/合并）
  - `handle(...)`：统一处警入口
  - `recover(...)`：恢复流程
- `OfflineInspectionTask`
  - 定时扫描离线设备并触发离线告警
- `AlarmController / MonitorController / DeviceController / AreaOrgController`
  - 对外业务查询与处警接口

## 第3章 数据库设计（ECMS）与关系图

表命名规则：`ECMS_D_ST_*`

### 3.1 主数据表（必须先有）

- `ECMS_D_ST_AREA`：场所树（到 SHAFT 层）
- `ECMS_D_ST_ORG`：组织树（与 area 同结构且同数据）
- `ECMS_D_ST_SHAFT_DEVICE`：设备表
- `ECMS_D_ST_MONITOR`：监测对象（竖井）
- `ECMS_D_ST_SHAFT_FLOOR`：楼层对象
- `ECMS_D_ST_MONITOR_DEVICE_BIND`：监测对象-设备绑定
- `ECMS_D_ST_MONITOR_PARTITION_BIND`：分区绑定（最关键映射表）
- `ECMS_D_ST_ALARM_RULE`：规则配置（基础配置，需预置）

### 3.2 运行增量表

- `ECMS_D_ST_RAW_DATA`：测温原始数据
- `ECMS_D_ST_ALARM_RAW`：告警原文数据
- `ECMS_D_ST_ALARM`：告警主单
- `ECMS_D_ST_EVENT`：告警事件
- `ECMS_D_ST_DEVICE_ONLINE_LOG`：在线离线变化日志

### 3.4 最关键映射字段（详细）

要正常接入 MQ，关键只需要对齐三项：

- `device_token`
  - 来源：`topic` 或 `payload.dataReference` 中的设备段
  - 必须匹配：`ECMS_D_ST_SHAFT_DEVICE.iot_code`
  - 要求：完全一致，区分大小写

- `partition_id`
  - 来源：`payload.PartitionId`（或同义字段 `partitionNo`）
  - 必须匹配：`ECMS_D_ST_MONITOR_PARTITION_BIND.partition_id`（同一 `device_token` 下）
  - 要求：数值一致，且该设备下存在该分区

- `data_reference`
  - 来源：`payload.dataReference`
  - 必须匹配：`ECMS_D_ST_MONITOR_PARTITION_BIND.data_reference`
  - 作用：当 `partition_id` 异常或缺失时做兜底定位

示例：

- topic  
  `/TMP/ft-shaft-dev-0014_TMP_th28/Measure`

- payload  
  `{"PartitionId":28,"dataReference":"/TMP/ft-shaft-dev-0014_TMP_th28","timestamp":"2025-04-21T02:50:29.190Z","MaxTemp":"38.4","MinTemp":"27.8","AvgTemp":"32.1"}`

对应关系：

- `device_token = ft-shaft-dev-0014`（来自 topic 或 dataReference）
- `partition_id = 28`（来自 payload.PartitionId）
- `data_reference = /TMP/ft-shaft-dev-0014_TMP_th28`（来自 payload.dataReference）

匹配顺序：

- 先用 `device_token + partition_id`
- 再用 `data_reference`
- 都匹配不到就会出现 `partition binding not found`

## 第4章 联调数据脚本（详细）

执行顺序：

1. `dock/福田区台账抽取_主数据初始化_ECMS.sql`
2. `dock/福田区台账抽取_接口联调初始化_ECMS.sql`

### 4.1 主数据脚本内容

- 3 个小区
- 共 14 栋（听水居：1/2/3/5栋；润雨居：1/2/3/5栋；鸣翠居：1/2/3/5/6/8栋）
- 每栋 1 个单元（SHAFT），共 14 个监测对象
- 14 台设备（`asset_status` 仅 `0/1`）
- 楼层口径按台账：听水居与润雨居均为 22 层；鸣翠居分别为 28/29/29/30/28/28 层
- 共 348 楼层、348 条分区绑定

### 4.2 联调数据脚本内容（当前版本）

- `alarm_rule`：默认不作为联调增量核心数据；如需覆盖场景可按脚本补充 5 条测试规则
- `raw_data`：2784 条（348分区 * 8）
- `alarm_raw`：1740 条（348分区 * 5）
- `alarm`：按脚本当前状态集合生成（仅 3 种状态）
- `event`：每条 alarm 固定 2 条（用于对齐 `event_count/merge_count`）
- `device_online_log`：按设备批量生成

时间范围：

- 以脚本中的 `TO_DATE('2026-05-13 ...')` 为锚点
- 通过分钟/天偏移形成分布，不是单一时刻

校验语句（脚本已内置）：

- `alarm.event_count / merge_count` 与 `event` 数量一致性
- `alarm.device_name / monitor_name` 与主表一致性
- 告警状态分布检查

## 第5章 端到端链路（对照联调数据详解）

本章按“完全不熟悉系统”的视角说明从 MQTT 到告警落库。

### 5.1 接收测温消息（Measure）

1. `iotservice` 收到 topic + payload  
2. 转发到 `onlineservice` 批量接口  
3. `DeviceResolverService` 解析绑定：
   - 优先：`iotCode + PartitionId`
   - 次优：`dataReference`
   - 再次：`partitionCode`
4. 命中后得到：`device_id/monitor_id/shaft_floor_id`
5. 落库：
   - `raw_data` 写一条
   - Redis 更新最近状态与窗口
6. 规则引擎评估
7. 命中则进入 `createOrMerge`

### 5.2 接收告警原文（Alarm）

1. `iotservice` 转发 `AlarmStatus/FaultStatus` 原文
2. `onlineservice` 写 `alarm_raw`
3. 可作为终端告警判定输入（按当前规则实现）

### 5.3 生成主告警与事件

1. `AlarmMergeService.createOrMerge(...)`
2. 待确认状态允许合并（按 merge_key）
3. 事件写入 `event`（受限频策略影响）
4. 更新 `alarm.last_alarm_time / merge_count / event_count`

### 5.4 离线巡检补充链路

1. `OfflineInspectionTask` 定时扫设备最近上报时间
2. 超阈值触发 `DEVICE_OFFLINE`
3. 同样走 `createOrMerge` 与 `event` 写入流程

## 第6章 告警规则（详细）

### 6.1 规则来源与位置

规则表：`ECMS_D_ST_ALARM_RULE`  
加载类：`AlarmRuleResolverService`（定时刷新）

### 6.2 当前规则类型

- `TEMP_THRESHOLD`（定温）
- `TEMP_DIFFERENCE`（差温）
- `TEMP_RISE_RATE`（升温速率）
- `DEVICE_OFFLINE`（设备离线）
- `PARTITION_FAULT`（分区断纤）

### 6.3 字段与单位

- `threshold_value`
  - 温度类：摄氏度（℃）
  - 离线类：秒阈值（结合实现）
- `threshold_value2`
  - 备用副阈值（按规则类型是否使用）
- `duration_seconds`
  - 持续时长（秒），用于速率/持续判断
- `enabled`
  - 1 启用，0 停用

### 6.4 规则生效链路

1. ingest 进来后构造规则上下文
2. `AlarmRuleEngine` 输出命中结果
3. 命中则构造 `RuleEvaluationResult`
4. 进入 `AlarmMergeService.createOrMerge`

## 第7章 核心 Controller 详解

### 7.1 `IotIngestController`

用途：接收 iotservice 转发数据。  
重点接口：

- 测温批量入站
- 告警原文批量入站

关注点：

- 入参字段完整性（`topic/iotCode/PartitionId/dataReference/timestamp`）
- 批量失败处理策略（单条失败不拖垮全批）

### 7.2 `AlarmController`

用途：告警查询与处警。  
重点接口：

- 告警列表（筛选：状态、类型、时间、区域）
- 统一处警 `handle`（按状态码流转）
- 告警详情/事件列表

关注点：

- `status` 枚举值必须和 `AlarmStatus` 一致
- 处警后是否触发了对应事件

### 7.3 `MonitorController`

用途：监测对象查询与统计。  
重点能力：

- 按区域树查询竖井/楼层
- 列表扩展实时字段（今日是否告警、温度统计、最近时间）

### 7.4 `DeviceController`

用途：设备台账、接入状态、在线状态。  
重点能力：

- 设备分页查询（类型、接入状态、机构等）
- 批量接入确认
- 在线状态辅助展示

### 7.5 `AreaOrgController`

用途：区域/组织树查询、模板下载、导入等。  
关注点：

- area 与 org 的层级一致性
- 路径字段 `path_ids/path_names` 正确性

## 第8章 常见排障与对接问题（新增）

### 8.1 报错：`partition binding not found`

含义：消息无法映射到分区绑定。  
排查顺序：

1. 看 `iot_code` 是否大小写一致
2. 看 `PartitionId` 是否在绑定表存在
3. 看 `dataReference` 与 `partition_code` 是否匹配
4. 看绑定是否被软删

### 8.2 报错：`Device not found for binding deviceId=...`

含义：绑定表有设备ID，但设备表无有效记录。  
当前优化：启动与刷新缓存时已改为“跳过脏绑定并打印日志”，不阻塞启动。

新增日志说明：

- `warn`：`Skip invalid partition binding ...`
  - 表示某条绑定脏数据被忽略
  - 关注字段：`bindingId/deviceId/monitorId/partitionCode`
- `info`：`Partition binding cache refreshed: total=..., valid=..., skipped=...`
  - 代表本次刷新总体质量
  - `skipped > 0` 需清洗绑定数据

### 8.3 `alarm.event_count` 与 `event` 数量不一致

常见原因：联调造数逻辑独立生成，口径不一致。  
处理建议：联调脚本强制按 `event` 反推并校验。

### 8.4 `alarm.device_name/monitor_name` 与主表不一致

常见原因：冗余字段未按主表回填。  
处理建议：造数时 join 主表写入，不手拼路径。

### 8.5 告警不合并

排查：

1. 当前状态是否仍允许合并（待确认）
2. `merge_key` 是否一致
3. 是否被事件限频误判为“没写事件”（合并可能成功但事件被节流）

### 8.6 对接前检查清单

- MQTT topic 设备段、payload 字段完整
- 主数据脚本与联调脚本按顺序执行
- 规则表已初始化并启用
- Redis/MySQL 连通正常
- 绑定缓存刷新日志 `skipped=0` 或可解释
